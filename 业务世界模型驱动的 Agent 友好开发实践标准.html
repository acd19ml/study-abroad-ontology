从 0 到 1 落地一个业务场景

1　关于本标准

本标准规定一线团队如何以业务世界模型为单一权威源，在一个业务场景内完成从建模、代码生成到 agent 运行和反馈演化的 0 到 1 落地。

目的。代码生成的成本已大幅下降，瓶颈转移到“说清楚要什么”和“证明做对了”。本标准把业务知识沉淀为显式、结构化、版本化的模型，让代码、文档、agent 的工具和约束都从模型派生或受模型约束，并让运行反馈回流修正模型。

适用范围。适用于一个限界上下文内的单个业务场景，可以是新建系统，也可以是存量系统改造。不适用于不含业务规则的纯技术组件。向多个上下文推广，应在至少一个场景完成闭环后另行规划。

目标读者。业务分析、架构与开发、数据、算法、测试等一线实施人员，以及对业务规则负最终责任的业务方。

用语 含义
必须 / 不得 强制要求，不满足即视为不符合本标准
应当 / 不应 推荐做法；偏离时必须在架构决策记录中写明理由
可以 可选做法

如何使用。按第 8 章的阶段顺序推进，每个阶段满足通过标准后再进入下一阶段。第 5 至 7 章是各阶段产出物的规范依据，附录提供可直接复制的模板和检查表，第 12 章预留贯穿案例。其他章节中的订单、退款示例仅为示意，最终以第 12 章案例为准。

2　术语与定义

本标准中的术语按下表理解；同一术语在团队文档、模型文件和代码中必须保持同一含义。

术语 定义
业务世界模型 对一个业务领域的显式、结构化、版本化描述，包括目标、指标、业务对象、关系、状态、命令、事件、规则、策略、角色及其到实现的映射
事实源 业务方对业务的陈述，以及业务方提供的原始材料（合同、SOP 等）；模型从事实源派生，业务含义有争议时回到事实源核对【v1.1】
元模型 规定业务世界模型由哪些元素类型构成、各有哪些属性、允许哪些关系的“模型的语法”
模型源 业务世界模型的唯一权威存放位置，所有修改只发生在这里
投影 由模型源自动生成的产物，如领域代码骨架、agent 工具定义、规则库条目、文档与图、图谱、检索索引；投影可随时重建
限界上下文 一个概念含义保持一致的业务范围；同一词语在不同上下文中可以有不同定义
业务对象 业务中有身份、有生命周期的事物，如订单、退款单
聚合 / 聚合根 必须作为整体保持一致的一组业务对象；聚合根是外部修改该组对象的唯一入口
命令 定义在聚合根上的业务动作，是改变业务状态的唯一方式
事件 命令执行后产生的、表示业务事实已经发生的记录
不变量 在一个聚合内任何命令执行后都必须成立的规则，违反即拒绝
策略 某事件发生后触发另一个聚合命令的跨聚合协调规则，允许最终一致
规范性知识 必须被遵守的规则，由系统强制执行
参考性知识 供判断参照的知识，如历史案例、背景说明，允许偏离但须留痕
人工决策点 模型中明确标注的、由人而非规则或模型作出判断的位置
控制层 运行时位于 agent 与业务系统之间的组件集合，负责组装上下文、执行硬约束、降级与留痕
模型版本 模型源某一次评审合入后的快照；同一版本生成的全部投影作为整体发布
验收问题集 在建模之前依据已确认需求编写、由业务方确认标准答案的问题集合，题目只用业务语言，用来检验模型及其承载形态是否可用；分为建模时可参考的开发集，和建模者不可见的留出集【v1.2】
纵向切片 一组能端到端验证的用户故事，连同它们的验收问题、涉及的模型片段和对应的交付；迭代以切片为单位推进【v1.2】
发现轨、交付轨 发现轨负责需求、验收问题和模型，交付轨负责架构决策、生成实现和运行验证；一个切片先过发现轨再进交付轨【v1.2】
元模型冻结 模型的表达标准（元素类型和字段）不再随切片调整的时点；冻结后新增元素类型须走本标准的修订流程【v1.2】

3　核心原则

以下八条原则是本标准所有条款的依据；具体条款与原则冲突时，以原则为准并修订条款。

  1. 模型是资产，代码是投影。业务含义必须首先体现在模型中。代码、文档、agent 工具都是模型的投影，不得成为某条业务规则的唯一出处。
  2. 单一权威源。模型源是系统和 agent 的唯一权威源，其内容派生自事实源（见第 2 章）。模型只有一个修改入口。投影只能由流水线生成，不得手工修改；需要改变投影时，必须修改模型源或生成器。
  3. 生成廉价，验证昂贵。每一类生成物必须有对应的自动验证。没有验证手段的产物不得进入发布。团队应把节省下来的编码时间投入到建模和验证。
  4. 契约优于上下文。规范性约束必须由系统在执行时强制检查，不得只写在提示词或文档里。安全不依赖于 agent 是否“看到”了规则。
  5. 规范与参考分离。每条规则必须标注为规范性或参考性。规范性的强制执行；参考性的供判断参照，偏离时放行并留痕。
  6. 不强行规则化。无法穷举、依赖情境判断的业务知识不得硬写成规则，必须标注为人工决策点，并附自然语言的判断指引。
  7. 稳定标识连接一切。每个模型元素必须有稳定唯一的 ID。投影、文档、代码、运行日志都通过 ID 引用模型元素，信息分布在多处但始终可以确定地关联和重组。
  8. 小步起步，在运行中生长。从一个场景、少量核心对象和规则起步。场景只有在“运行反馈回流修正模型”的闭环至少完整跑通一次后，才算完成 0 到 1。

4　总体架构

Agent 友好架构以业务世界模型为单一权威源，划定业务、确定性、人机、生成四类边界，以可验证的契约约束 AI 参与系统的构建与运行，使系统在成本可控的前提下满足业务目标，并通过模型的演进实现系统的演进。

模型源经校验后一次性生成全部投影并整体部署；运行中的追踪记录和人工修正，以变更提案的形式回到模型源。

引入 AI 后，架构的每个要素都发生了变化，本标准的条款正是针对这些变化制定的：

要素 传统软件架构 本标准的做法
边界 模块、服务、数据所有权 增加确定性、人机、生成三类边界（6.1）
决策 由架构师做出，记录在文档或脑中 显式写入模型和架构决策记录，agent 在其约束内工作
成本 主要是开发成本 开发成本下降，验证、治理和推理成本上升；投入转向建模与验证
业务目标 写在需求文档中，与系统间接关联 写入模型价值层，通过指标与系统行为直接相连
演进 修改代码，受编码速度限制 修改模型、重新生成、反馈回流，受验证速度限制

5　业务世界模型规范

业务世界模型必须按本章的元模型编写，存放在模型源中，并通过 5.7 节的全部校验后方可合入。本标准以 YAML 文件加 Git 作为参考实现；采用其他载体时，必须同时满足单一修改入口、版本可比对、合入需评审、可自动校验四项要求。

5.1　元模型分层

模型元素分为三层：价值层回答“为什么做”，业务层回答“是什么、怎么做、谁来做”，实现映射层回答“在哪里落地”。

元素 层 必填属性 说明
目标 价值 名称、描述、负责人 场景要达成的业务结果
指标 价值 名称、口径、统计对象或事件、关联目标 口径必须引用模型中的对象或事件
限界上下文 业务 名称、范围说明 所有业务层元素必须归属一个上下文
业务对象 业务 名称、属性、所属聚合 属性须注明业务含义和类型
关系 业务 源、目标、类型、基数 类型为组合、引用或关联之一
状态 业务 所属对象、状态列表、合法转换 每个转换必须由某个命令触发；状态隶属于所属对象，以“对象 ID + 状态值”标识，不单设 ID 前缀【v1.1】
聚合 业务 根对象、成员对象、不变量 见 5.4
命令 业务 所属聚合根、执行角色、参数、前置状态、状态转换、产生事件、执行等级（阶段 3 起必填）【v1.1】 改变业务状态的唯一方式
事件 业务 产生命令、携带数据 供策略、追踪与指标使用
规则 业务 约束强度、作用对象、条件、动作、来源 见 5.5
策略 业务 触发事件、目标命令、时限要求 跨聚合协调，最终一致
角色 业务 名称、类型（人或 agent）、可执行命令【v1.1】 人或 agent 都可以是角色
人工决策点 业务 所在命令或规则、判断指引、负责角色 见 5.5
实现映射 实现 模型元素、实现类型、实现位置 实现类型为表、字段、接口或服务

5.2　通用属性

每个模型元素除 5.1 的必填属性外，还必须具备以下属性：

  • id：稳定唯一标识，见 5.3。
  • status：draft、active、deprecated 之一。废弃元素不得直接删除，必须保留到所有引用清除为止。
  • owner：对该元素内容负责的角色。
  • since：首次生效的模型版本。
  • refs：关联的非结构化知识位置，如 SOP 段落、决策记录、案例，可以为空；但业务层元素由 draft 变为 active 之前，refs 必须至少指向一条事实源，没有事实依据的元素只能保持为提案【v1.1】。

5.3　标识规范

  • ID 格式为 <类型前缀>.<上下文>.<名称>，只使用小写英文字母、数字和下划线，例如 cmd.aftersales.approve_refund。
  • 类型前缀：goal metric ctx obj rel agg cmd evt rule pol role hdp map。
  • ID 一经生效不得修改或复用；改名只改 name 字段。
  • 中文名称写在 name 字段，供人阅读和 agent 理解。

5.4　聚合与读写视图

  • 每个命令必须属于且只属于一个聚合根。
  • 聚合内部的成员对象不得定义命令；修改成员对象的命令必须定义在根上。
  • 组合关系只能存在于聚合内部；跨聚合必须使用引用关系，只保存对方 ID。
  • 必须在一次命令内同步满足的规则，定义为该聚合的不变量；允许延迟满足的跨聚合规则，必须定义为策略。
  • 关联关系服务于读取，不受聚合边界限制，可以跨聚合定义，用于查询、分析和上下文组装。
  • 聚合应当尽量小：只有确实需要强一致的对象才放进同一个聚合。

5.5　规则与人工决策点

  • 每条规则必须标注约束强度：normative（规范性）或 reference（参考性）。
  • 规则条件必须引用模型中的业务概念，如对象属性、状态、事件、指标，不得直接引用数据库表或字段。概念与字段的对应关系写在实现映射中。
  • 规则条件必须能被机器解析，以便 5.7 的概念引用校验：只引用对象属性、状态、事件、指标或命令参数，用实施方定义的受限表达式书写，表达方式记入架构决策记录。下方示例中的条件为示意写法【v1.1】。
  • 规范性规则的动作必须取以下值之一：allow、deny、escalate（转人工）、flag（放行并标记复核）。
  • “较大”“频繁”“高风险”等模糊措辞必须量化为明确阈值；无法量化时不得写成规则，必须建立人工决策点。
  • 规则的例外必须逐条枚举；无法穷举时，必须建立人工决策点。
  • 人工决策点必须包含判断指引：需要考虑的因素、可参考的同类案例、负责角色。
# 示意：一个命令、一条规范性规则、一个人工决策点
- id: cmd.aftersales.approve_refund
  type: command
  name: 批准退款
  aggregate: agg.aftersales.refund
  role: role.aftersales.service_agent
  params: [refund_id, approved_amount]
  allowed_in: [已申请]
  transition: 已申请 -> 已批准
  emits: evt.aftersales.refund_approved
- id: rule.aftersales.refund_amount_cap
  type: rule
  name: 批准金额不超过订单实付金额
  strength: normative
  applies_to: cmd.aftersales.approve_refund
  condition: approved_amount > 订单.实付金额
  action: deny
  refs: [sop.aftersales.v3#4.2]
- id: hdp.aftersales.special_compensation
  type: human_decision_point
  name: 特殊情况补偿
  at: cmd.aftersales.approve_refund
  owner: role.aftersales.supervisor
  guidance: 结合客户历史投诉、实际损失和舆情风险判断；参考案例库中的同类案例

5.6　非结构化知识

  • SOP 原文、背景说明、决策理由、历史案例存放在文档系统或案例库中，不得写入模型源。
  • 每份非结构化材料必须标注关联的模型元素 ID；模型元素通过 refs 指回。
  • 同一条知识同时存在编译后的规则和 SOP、外部文档原文时，两者冲突以规则为准，原文必须标注为待更新；规则与业务方本人的陈述（事实源）冲突时，视为模型派生错误，必须修正模型【v1.1】。

5.7　文件组织与校验

model/
  meta/                 # 元模型 schema，见附录 A
  contexts/<上下文>/
    value.yaml          # 目标与指标
    objects.yaml        # 业务对象、关系、状态
    aggregates.yaml     # 聚合、命令、事件、不变量
    rules.yaml          # 规则与人工决策点
    policies.yaml       # 策略
    roles.yaml          # 角色
    mappings.yaml       # 实现映射
docs/                   # 非结构化知识，按 ID 关联
generated/              # 投影输出，禁止手改

模型的每次合入必须通过以下全部校验：

校验项 要求
结构 所有文件符合元模型 schema
引用完整 所有 ID 引用指向存在且未废弃的元素
聚合封装 每个命令属于一个聚合根；成员对象没有命令；组合关系不跨聚合
状态闭合 每个状态转换都有触发命令；没有不可达状态
规则完整 每条规则有约束强度、作用对象和来源；规范性规则的动作取值合法
概念引用 规则条件只引用模型概念，不含表名或字段名
指标可算 每个指标的统计对象或事件都存在
角色覆盖 每个命令都有执行角色
映射覆盖 每个命令和业务对象至少有一个实现映射，从阶段 4 起强制

6　Agent 友好架构规范

Agent 友好架构以业务世界模型为单一权威源，划定四类边界，生成投影，并在运行时执行仲裁，让 AI 在可验证的约束内参与系统的构建与运行。

6.1　四类边界

每个命令都必须在四类边界上有明确归属，划定结果记录在模型和架构决策记录中。

边界 回答的问题 划定依据 记录位置
业务边界 哪些对象属于同一上下文、同一聚合 概念含义是否一致；哪些规则必须强一致 上下文与聚合定义
确定性边界 哪些判断由规则决定，哪些交给模型 能否量化和穷举；出错代价 规则的约束强度；人工决策点
人机边界 agent 能否直接执行某个命令 可逆性、影响范围、合规要求 命令的执行等级
生成边界 哪些代码由模型生成，哪些手写 能否由模型完整描述 生成配置与扩展点声明

人机边界的执行等级必须取以下四级之一：

执行等级 含义
自动执行 agent 直接执行，事后按比例抽检
执行后复核 agent 执行，结果进入人工复核队列
执行前确认 agent 提出方案，人工确认后执行
仅人工 agent 只提供信息和建议，由人执行

不可逆或涉及资金的命令，在首个场景中不应设为自动执行，直到第 8 章阶段 5 的验证报告证明其可靠。

6.2　投影体系

投影 主要消费者 0→1 阶段要求
领域代码骨架 开发人员、编码 agent 必须
测试骨架 持续集成 必须
规则库条目 控制层 必须
文档与图 团队成员、业务方 必须
agent 工具定义 业务 agent 场景含业务 agent 时必须
指标定义 报表、分析类 agent 应当
图谱 影响分析、上下文组装 可以
检索索引 参考知识检索 可以
  • agent 工具必须由命令生成，一个命令对应一个工具。
  • 不得向 agent 暴露模型之外的写入能力，如通用 SQL 执行、通用数据更新接口。
  • 只读查询工具可以按关联关系生成，不受聚合边界限制。

6.3　运行时仲裁

agent 的每一个命令调用都必须经过控制层，按下表处理：

情形 处理 必须留痕的内容
违反规范性规则或不变量 拦截，按规则动作拒绝或转人工 命中的规则 ID 与模型版本
命中转人工规则或人工决策点 挂起，转给负责角色 人工决定及理由
模型或评分置信度不足 降级：限制可用工具、转人工复核或提高抽检比例 置信度与降级方式
偏离参考性知识 放行 偏离点，供规则提炼
规则与模型均未覆盖 转人工 人工判断，作为案例或规则候选
  • 降级阈值必须在模型或配置中显式声明，不得写死在代码中。
  • 人工驳回和修正必须填写理由。只点按钮、没有理由的驳回，不得作为规则提炼的依据。

6.4　上下文组装

  • 必须由统一的组装组件为所有 agent 组装业务上下文，不得在各 agent 的提示词中各自拼装业务知识。
  • 组装应当以命令为单位，取出该命令的闭包：所属聚合定义、不变量、前置状态、相关规则与策略、人工决策点及判断指引、关联案例与文档。
  • 业务对象的当前状态必须在执行时通过工具从业务系统读取，不得使用模型中的副本。
  • 每段上下文必须标注来源类型（规则、参考知识、实时数据）和模型版本。
  • 闭包中必需的元素缺失时，组装组件必须报告缺失，控制层按置信度不足处理。

6.5　整体发布与版本

  • 同一模型版本生成的全部投影必须作为一个整体发布，不得部分更新。
  • 运行时必须锁定所用的模型版本，每条运行记录必须包含模型版本号。
  • 回滚以模型版本为单位进行。

6.6　双重防线

控制层的执行前检查是第一道防线，领域代码中的不变量和前置状态检查是第二道防线。

两道防线必须由同一模型生成，并且必须同时存在；任何一方都不得因另一方存在而省略。

7　从模型到代码

代码中能由模型完整描述的部分必须由模型生成；模型无法描述的部分在声明过的扩展点中编写；两者的一致性由持续集成自动验证。本章的“手写”指不经模型生成器产出的代码，可以由人编写，也可以由编码 agent 编写。

7.1　生成范围

产物 来源 产出方式 能否手改
聚合类与成员对象 聚合、业务对象 生成 不得
命令处理入口 命令 生成 不得
前置状态与状态转换检查 状态、命令 生成 不得
不变量与规范性规则检查 不变量、规则 生成 不得
事件定义与发布 事件 生成 不得
策略的订阅与触发 策略 生成 不得
对外接口与 agent 工具定义 命令、关联关系 生成 不得
持久化映射 实现映射 生成或手写 手写时必须登记在实现映射中
命令内的业务计算 扩展点 手写 可以
外部系统适配 扩展点 手写 可以
不变量、状态转换、权限测试 模型 生成 不得
业务场景测试 场景画布、案例 以手写为主 可以

7.2　生成代码与手写代码共存

  • 生成代码与手写代码必须放在物理上分开的目录或文件中。生成文件头部必须标注生成所用的模型版本和“禁止手改”。
  • 扩展点必须在模型中声明，如命令的计算钩子、外部适配器接口；生成器据此生成接口或空实现。
  • 重新生成不得覆盖手写代码。扩展点签名变化时，生成器必须列出受影响的手写文件。
  • 手写代码不得绕过聚合根修改业务状态，不得新增模型之外的写入接口。

7.3　一致性验证

持续集成必须在每次提交时执行以下检查：

检查 要求
生成区未被改动 生成区文件与按当前模型版本重新生成的结果逐字一致
命令覆盖 每个命令都有实现入口；场景含业务 agent 时都有对应工具
无旁路写入 代码中不存在模型之外的业务状态写入路径
生成测试通过 不变量、状态转换、权限测试全部通过
规则同源 控制层规则库与领域代码中的检查来自同一模型版本

7.4　编码 agent 使用规范

  • 交给编码 agent 的任务必须附带：相关聚合的模型片段（按 6.4 的闭包组装）、相关架构决策记录、扩展点签名和验收测试。
  • 编码 agent 只能修改扩展点内的代码和业务场景测试，不得修改生成区，不得直接修改模型源。
  • 编码 agent 发现模型缺失或矛盾时，必须提出模型变更提案，不得在代码里自行补写规则。
  • 改变业务规则必须改模型，不得只改代码。

7.5　从模型变更到代码上线

  1. 提交模型变更提案。
  2. 模型校验通过，按第 9 章完成评审并合入。
  3. 重新生成全部投影。
  4. 补充或调整受影响的扩展点代码。
  5. 持续集成全部检查通过。
  6. 整体发布新的模型版本。

8　从 0 到 1 实践流程

一个场景的落地分为八个阶段，每个阶段的通过标准全部满足后才能进入下一阶段；阶段 7 的反馈闭环跑通一次，场景才算完成 0 到 1。

阶段是否通过，必须由 9.2 中该阶段标 A 的角色明确确认并留下记录；agent 可以对照通过标准核对并报告结果，不得自行宣布通过【v1.1】。

阶段 0 至 7 是一块业务的完整路径；实际推进时，按纵向切片沿发现轨和交付轨迭代，切片步骤、就绪与完成定义、编码起点、模型可用性验证和风险见 8.1–8.7【v1.2】。

阶段 0 至 6 依次通关；阶段 7 把运行中的知识带回建模，形成之后每一轮迭代的入口。

阶段 0

场景选定

目标：选定一个价值明确、边界清楚、风险可控的场景，并定义成功标准。

  1. 列出候选场景，从业务价值、规则清晰度、边界是否单一、出错是否可逆、数据是否可得五个方面评估。
  2. 选定一个场景，范围限定在一个限界上下文内。
  3. 定义业务目标和一到三个可度量指标，记录当前基线值。
  4. 约定阶段 5 的验证通过阈值。
  5. 写明范围内和范围外的内容，确定参与角色。

产出物：场景画布（附录 B.1）。

通过标准
  • 目标至少对应一个有基线值的指标
  • 验证通过阈值已写入场景画布
  • 范围限定在一个限界上下文内，范围外内容已列明
  • 业务方已指定规则负责人

常见问题：首个场景选得过大，跨越多个部门。首个场景应当高频、规则较明确、有人工兜底、出错可逆。

阶段 1

业务发现

目标：把场景中的事件、动作、对象、规则和例外完整地摆出来。

  1. 组织事件风暴工作坊：按时间顺序列出领域事件，再补上触发事件的命令和角色、命令作用的对象、约束命令的规则和跨对象的策略，标出疑问。
  2. 从存量代码、表结构、SOP、工单中逆向抽取候选对象、状态和规则。可以用 LLM 起草，但每一项必须由人核对。
  3. 收集例外情形和依赖人工判断的历史案例。
  4. 整理未决问题清单，每个问题指定负责人。
  5. 编写需求文档：以用户故事和验收标准描述需求，每条注明事实源出处，区分业务方已确认的内容与推断【v1.1】。
  6. 梳理用例：覆盖需求的主流程、备选流程和异常流程【v1.1】。可以采用路径清单形式，每条路径至少对应一道验收问题【v1.2】。
  7. 编写验收问题集：只依据已确认的需求出题，业务方逐题确认标准答案；业务方另写一批留出问题，建模者不可见（8.2 的 S2、S3）【v1.2】。

产出物：事件流、候选元素清单、未决问题清单、SOP 与案例索引、需求文档、用例规格【v1.1】、验收问题集【v1.2】。

通过标准
  • 业务方确认事件流覆盖主流程和主要异常流程
  • 每条候选规则都有出处
  • 每个未决问题都有负责人
  • 业务方已审阅需求文档和用例【v1.1】
  • 业务方已确认首个切片验收问题的标准答案【v1.2】

常见问题：只梳理主流程，忽略异常流程；LLM 抽取结果未经核对就进入建模；没有需求文档和用例就从访谈直接建模，业务方无从核对模型【v1.1】。

阶段 2

建模

目标：产出第一版通过校验、经业务方确认的模型源。

  1. 划定限界上下文和聚合。
  2. 编写业务对象、关系和状态。
  3. 编写命令和事件。
  4. 按附录 B.4 把 SOP 迁移为规则，标注约束强度，为无法规则化的部分建立人工决策点。
  5. 定义指标口径。
  6. 把每个模型元素追溯到需求文档和事实源【v1.1】。
  7. 运行模型校验并修正。
  8. 运行静态验证：每道已确认的验收问题都能在模型中找到完整依据；条件允许时运行消费验证（8.6 第 1、2 级）【v1.2】。
  9. 业务方评审。

产出物：模型源 v1，以及由它生成的文档与图。

通过标准
  • 通过 5.7 的全部校验（映射覆盖除外）
  • 业务方已确认全部规范性规则
  • 每个人工决策点都有判断指引
  • 已确认验收问题的依据覆盖率为 100%【v1.2】

常见问题：规则条件直接写字段名；模糊措辞未量化；把所有对象放进一个大聚合。

阶段 3

架构决策

目标：为每个命令划定四类边界，并把决策写下来。

  1. 为每个命令确定业务、确定性、人机、生成四类边界的归属。
  2. 为每个命令确定执行等级。
  3. 确定降级阈值和人工介入流程。
  4. 在模型中声明扩展点。
  5. 确定投影清单和技术栈。
  6. 编写架构决策记录（附录 B.3）。

产出物：架构决策记录、更新后的模型、投影清单。

通过标准
  • 每个命令都有执行等级
  • 涉及资金或不可逆的命令未设为自动执行，或已记录理由
  • 扩展点已在模型中声明
阶段 4

生成与实现

目标：从模型生成可运行的系统和全部投影。

  1. 补全实现映射。
  2. 生成全部投影。
  3. 实现扩展点，可以由人或编码 agent 完成，须遵守 7.4。
  4. 搭建控制层和上下文组装组件。
  5. 配置 7.3 的持续集成检查。

产出物：可运行系统、全部投影、持续集成流水线。

通过标准
  • 7.3 的全部检查通过
  • 映射覆盖校验通过
阶段 5

验证

目标：证明系统和 agent 的行为符合模型与业务预期。

  1. 运行全部生成测试。
  2. 复用阶段 1 的验收问题集作为业务场景评测集，补充来自事件流、例外情形和历史工单的题目，并回归此前全部切片【v1.2】。
  3. 评测 agent 行为：结果是否正确、拦截是否正确、转人工是否恰当。
  4. 进行对抗测试，尝试诱导 agent 越权或绕过规则。
  5. 业务方抽样复核。

产出物：验证报告。

通过标准
  • 硬约束违反次数为 0
  • 评测集通过率达到阶段 0 约定的阈值
  • 业务方已签字确认
阶段 6

上线运行

目标：在可观测、可回滚的前提下让场景进入真实业务。

  1. 灰度上线：先以较保守的执行等级运行，再根据数据逐步提升。
  2. 开启全链路追踪。
  3. 建立人工介入队列和值班安排。
  4. 按第 10 章监控指标。

产出物：运行中的系统、指标看板。

通过标准
  • 每条运行记录都包含模型版本和命中的规则
  • 第 10 章的必选指标均可观测
  • 已完成一次回滚演练
阶段 7

反馈演化

目标：让运行中产生的知识回流到模型，完成第一次闭环。

  1. 定期复盘人工驳回与修正、偏离参考知识的记录、转人工高发点和未覆盖情形。
  2. 把可以规则化的判断整理成模型变更提案；把典型判断收入案例库。
  3. 按 7.5 发布新的模型版本。
  4. 对比新旧版本的指标。

产出物：模型 v2、变更记录、复盘纪要。

通过标准
  • 至少一项来自运行反馈的模型变更已发布
  • 新版本的关键指标不劣于旧版本

8.1　阶段与迭代【v1.2】

阶段 0 至 7 描述的是一块业务从发现到反馈的完整路径。实际推进时，不要求整个场景走完阶段 2 才进入阶段 3，而是把场景切成若干纵向切片，每个切片沿两条轨道推进：

  • 发现轨：需求、验收问题、模型扩展和模型验证，对应阶段 1、2；
  • 交付轨：架构决策、生成与实现、运行验证，对应阶段 3 至 5；
  • 回流：试用和运行中发现的问题，以变更提案或新的验收问题回到下一个切片的发现轨，对应阶段 6、7。

同一切片内，阶段顺序不能跳；不同切片可以错开，一个切片在交付轨上实现时，下一个切片已在发现轨上建模。

工程效率 生成代码占比 生成区代码行数占全部业务代码行数的比例 代码仓库统计 应当
工程效率 一致性检查失败次数 7.3 检查失败的次数，按检查项分组 持续集成 应当
成本 单次任务推理成本 每次 agent 任务消耗的模型调用费用 模型调用日志 应当
成本 人工介入工时 处理人工介入队列花费的工时 人工介入队列 应当

人工介入率和人工推翻率需要一起看：介入率下降而推翻率上升，说明 agent 的自主范围扩得过快。

11　反模式与风险

下表列出实施中最常见的十二种偏差【v1.2】；出现任何一种，都应当在下一次复盘中处理。

反模式 表现 后果 对策
大一统建模 一开始就为全公司建模 周期过长，建完业务已变 一个场景、一个上下文起步（原则 8）
过度规则化 把依赖情境的判断硬写成规则 规则僵化，例外不断 建立人工决策点（5.5）
手改投影 直接改生成代码、规则库或图谱 源与投影分叉 生成区一致性检查（7.3）
规则只在提示词里 规范性约束只写进 agent 提示词 agent 可能忽略规则 控制层强制执行（6.3）
规则绑定字段 规则条件直接写表名、字段名 表结构一变规则失效 只引用模型概念（5.5）
各自组装上下文 每个 agent 自己拼装业务知识 同一问题得到不同判断 统一组装组件（6.4）
模型与代码漂移 在代码里改规则而不改模型 模型失去权威性 规则变更必须改模型（7.4）
无理由的驳回 人工驳回只点按钮 反馈无法转化为知识 驳回必须填写理由（6.3）
跳过反馈闭环 上线即结项 模型停止生长 阶段 7 是完成条件（第 8 章）
平台锁定 模型只存在于某个商业平台内部 迁移和多平台共存困难 模型源可导出为开放格式
按题建模【v1.2】 为每道验收问题各建一个元素 模型退化为问答库，换个问法就答不对 留出集与元素组合优先（8.2、8.7）
先写代码后补模型【v1.2】 模型未就绪就开始写产品代码，或让原型转正 业务规则散落在代码中，模型只能事后追认 区分验证性代码与产品代码，过“模型就绪”门后再写产品代码（8.5）
