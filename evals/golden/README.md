# 金标测试集构建标准

- 版本：v0.1（2026-11-10）
- 状态：构建标准已由用户确认（Q-085）；题目为草稿，标准答案待用户逐题确认。
- 对应需求：[产品需求文档 v0.1](../../docs/requirements/product-requirements-v0.1.md)

## 1. 用途

金标测试集在本项目中有三个用途：

1. **定义业务本体模型标准的依据。** 本体需要表达什么，由“答对这些题需要什么知识”来决定。
2. **选择承载和消费形态的裁判。** 同一套题拿去考不同的承载形态，按结果选择。
3. **回归测试。** 需求或模型变更后重跑。

核心要求：**金标与承载形态无关。** 题目、答案和依据只用业务语言书写，依据指向 PRD 条目和事实源，不出现模型元素、图谱节点、接口名称。

## 3. 题目结构

| 字段 | 必填 | 内容 |
|---|---|---|
| `id` | 是 | `GS-nnn`，一经使用不再改作他用 |
| `status` | 是 | `draft`（起草）、`confirmed`（用户确认）、`retired`（废弃，保留编号） |
| `type` | 是 | 题型，见第 4 节 |
| `level` | 是 | 推理层级 `L1`–`L4`，见第 5 节 |
| `phase` | 是 | `一期`：只读问答即可回答；`二期`：需要实例数据或执行能力 |
| `question` | 是 | 顾问口吻的自然语言问题 |
| `variants` | 否 | 同一题的其他问法 |
| `facts` | 否 | 本题假设的情景事实，每条都标“（假设）”或“（虚构）” |
| `expected_behavior` | 是 | `回答`、`拒绝执行`、`说明未定义`、`说明不提供`、`转顾问判断` |
| `conclusion` | 是 | 一句话结论，能明确判对错 |
| `must_include` | 是 | 回答必须包含的要点 |
| `must_not` | 否 | 出现即判错的内容 |
| `basis` | 是 | 依据：PRD 条目（BR、US、OQ）和事实源（B1–B9、C、Q-nnn） |
| `pair` | 否 | 与本题成对的正例或反例 |
| `paths` | 否 | 对应的用例路径（`UP-nnn`） |
| `quadrant` | 否 | 稳定性与控制强度：`稳态强控`、`稳态弱控`、`敏态强控`、`敏态弱控`。用于选择承载形态时分象限比较：强控制的题要看拦截是否由规则执行，敏态的题要看上下文质量（Q-086） |

## 4. 题型

| 题型 | 考什么 |
|---|---|
| 问规则 | 规则本身及其理由 |
| 问操作 | 流程与下一步 |
| 情景判定 | 给定事实，判断允许、拦截或未知 |
| 影响分析 | 某个变化影响哪些内容、哪些学生和项目 |
| 代查 | 在虚构实例数据上查询（二期） |
| 代操作 | 给出指令，判断执行、拦截或需要确认（二期） |
| 越界与未知 | 拒绝、说明不提供、说明尚未定义 |

## 5. 推理层级

| 层级 | 含义 |
|---|---|
| L1 直取 | 一条规则或一个事实即可回答 |
| L2 组合 | 需要把规则与状态，或两条以上规则组合起来 |
| L3 多步推导 | 需要情景事实，加上多条规则、状态和关系，例如影响分析、排序 |
| L4 例外与边界 | 涉及冲突、未知、未定义，或不允许越过的例外 |

## 6. 质量标准

每道题必须满足：

1. **依据只来自已确认的需求。** PRD 中标“待确认”的条目和未决问题，不能作为标准答案的依据，只能出成“期望行为：说明未定义”的题；用户确认后再升级为正式题。
2. **答案可判定。** 结论能明确判对错，不出“视情况而定”的题。
3. **正反成对。** 每条规范性规则至少一道“被拦住”的题和一道“被允许”的题。
4. **不含承载形态术语。** 题目和答案中不出现模型元素、节点、接口名称。
5. **情景数据全部虚构。** 不使用真实学生资料，并在 `facts` 中标注。
6. **标准答案由用户确认。** Agent 起草，用户确认后 `status` 改为 `confirmed`。只有已确认的题计入正式评测。

## 7. 开发集与留出集

为防止本体只会回答这些题（变成 FAQ），题目分两部分：

| 部分 | 编写 | 存放 | 使用 |
|---|---|---|---|
| 开发集 | Agent 起草、用户确认 | 本目录 | 设计本体标准时可以参考 |
| 留出集 | 用户用自己平时的问法写 15–20 道，只写问题 | 用户保管在仓库外 | 本体标准冻结后，比较承载形态时才交给 Agent，届时再起草标准答案交用户确认 |

开发集得分高、留出集得分低，说明在向 FAQ 过拟合。

## 8. 覆盖规则

| 覆盖对象 | 最低要求 |
|---|---|
| PRD 业务规则 BR-01 至 BR-30 | 每条至少一道反例（被拦住或不成立）和一道正例 |
| PRD 第 3.2、3.3 节的不提供与系统不做事项 | 每项至少一道越界题 |
| 用例路径（`use-case-paths.md`） | 每条至少一道题 |
| 题型 | 每种至少 5 道 |
| 推理层级 | L3、L4 合计不少于三分之一 |

预计第一版共 80–100 道，分批起草、分批确认。

## 9. 评分

每道题评四项：

| 项 | 判定 |
|---|---|
| 结论 | 与 `conclusion` 一致 |
| 要点 | `must_include` 全部覆盖 |
| 依据 | 引用的依据与 `basis` 一致或等价 |
| 越界 | 未出现 `must_not` 中的内容，未执行应拒绝的操作。越界一票否决 |

比较承载形态时，正确率之外还比较：

- **一致性**：同一题多次运行，结论是否稳定；
- **可追溯**：回答的依据能否指回 PRD 和事实源；
- **强制执行**：代操作题的拦截，是靠系统规则还是靠 AI 自觉；
- **成本**：每题消耗的上下文长度和 API 费用。

## 10. 基线

第一个参照形态是“直接读 PRD”：把 PRD 全文作为上下文，让大模型答题。本体方案必须在推理层级、一致性、强制执行或成本上明显胜过它，才值得建设。每次运行都会产生 API 费用，先估算，经用户同意后再跑。

## 11. 版本

- 题目集的版本跟随 PRD 版本。PRD 变更时，列出依据受影响的题目，重新确认。
- 题目废弃时标 `retired`，不删除、不复用编号。
