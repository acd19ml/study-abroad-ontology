# ADR-002：语义服务的消费契约与分期

- 状态：提议
- 日期：2026-11-02
- 相关模型元素：全部命令、规则、人工决策点、策略、对象状态；模型版本清单 `model/model.yaml`
- 依据：[ADR-001](ADR-001-semantic-service-and-harness-boundary.md)；参考材料中的九项消费服务（C01–C09）与统一返回结构；实践标准第 6.2、6.4、6.5 节。

## 背景

Harness 需要从语义服务取得业务知识与判定，而不是读取模型源文件或代码仓。需要确定：语义服务提供哪些能力、返回什么结构、知识从哪里来，以及按什么顺序建设。

## 决策

### 1. 知识来源：模型知识包

生成器新增一个投影：**模型知识包** `generated/ps-model-knowledge.json`。它与 HTML 页面来自同一次生成、同一模型版本，内容包括：

- 全部模型元素及其属性、关系、状态转换、规则条件；
- 按 ID、中文名、属性含义及术语表 `CONTEXT.md` 建立的检索索引；
- 模型元素 `refs` 所指来源文档的正文快照，标注为“参考知识”；
- 模型版本号与生成器版本。

语义服务只读取知识包，不读取模型源或代码仓。知识包禁止手改，由 `render_model.py --check` 一并检查与模型同步（标准原则“单一权威源”）。

### 2. 第一版提供的能力（全部只读）

| 编号 | 参考材料对应 | 本项目能力 | 回答的问题 |
|---|---|---|---|
| S1 | C01 search_semantics、C03 的术语部分 | `search_model`：按词语查找相关对象、命令、规则、状态，返回候选和匹配依据 | 用户说的“定稿”“放弃”对应模型里的什么 |
| S2 | 资源读取 | `get_element`：取单个元素的完整定义、依据状态（已确认业务或 Agent 提案）、来源文档 | 这条规则具体怎么写的 |
| S3 | C02 get_semantic_context | `get_command_closure`：按标准第 6.4 节取命令闭包，包括所属聚合、前置状态与转换、作用于它的规则与不变量、人工决策点及指引、相关策略、执行角色与执行等级 | 记录已递交要满足什么、会有什么后果 |
| S4 | C04 resolve_business_solution（只读部分） | `get_state_actions`：给定对象与状态，返回此时允许的命令、执行角色、执行等级、目标状态及相关规则 | 现在是“英文已检查”，下一步能做什么 |
| S5 | C05 evaluate_business_rule | `evaluate_rule`：用用户描述的假设情景判定规则，返回命中 / 未命中 / 未知，以及缺少哪些事实 | 学生没确认中文能生成英文吗（规则判定由服务完成，不由大模型推理） |
| S6 | C09 get_business_evidence（只读部分） | `get_sources`：返回元素的来源文档及相关段落，标注为参考知识 | 这条规则的原始业务依据是什么 |

S5 只接受用户描述的假设事实，返回结果标明“假设情景”；第一版没有真实业务数据。

### 3. 统一返回结构

所有能力按同一结构返回，便于 Harness 判断下一步，也便于评测核对依据：

```json
{
  "status": "READY",
  "model_version": "0.1.0-draft",
  "result": {},
  "missing_facts": [],
  "applicable_rules": [],
  "evidence": [{"id": "rule.ps.final_known_requirements", "basis": "confirmed_business", "sources": ["docs/..."]}],
  "constraints": [],
  "next_actions": []
}
```

- `status` 取值：`READY`（可用）、`NOT_FOUND`（模型无此内容）、`NEEDS_FACTS`（判定缺少事实）、`INVALID_INPUT`（参数不合法）。是否有歧义、是否超出范围，由大模型依据检索候选与上下文范围说明判断，不由服务返回状态；理由见[设计文档](../design/semantic-service-v1.md)第 4 节。
- `evidence` 必须给出模型元素 ID；问答 AI 回答中的依据只能来自这里。
- `next_actions` 只是建议，不是执行授权（参考材料第四节）。

### 4. 分期

| 期 | 前提 | 新增能力（参考材料对应） | 对应 AI 客服能力 |
|---|---|---|---|
| 一期 | 本记录 | S1–S6 | 问规则、问操作 |
| 二期 | 阶段 4 建成业务系统与实现映射 | 结构化业务查询（C06），不接受任意 SQL；业务上下文解析（C03） | 代查 |
| 三期 | 控制层与执行前检查就绪（标准第 6.3、6.6 节） | 执行前检查（C07）、受控执行（C08）；执行工具由命令生成，一个命令一个工具 | 代操作 |
| 四期 | 运行追踪 | 全链路证据与回放（C09 完整版） | 解释与审计 |

三期有一个待决问题：顾问让 AI 代为执行“仅人工”命令（例如记录已递交）时，是顾问在网页上点确认就算人工执行，还是要把这类命令的执行等级改为“执行前确认”。这是人机边界决策，需业务方确认（标准第 9.3 节），到三期再定。

### 5. 对外形式

第一版的语义服务是一个 Python 模块，由网页问答 AI 在同一进程内调用。接口按上述契约固定，以后可以原样再提供为 MCP 服务：模型元素作为 Resource，S1–S6 作为 Tool，供其他 Harness 使用。是否以及何时提供 MCP 版本，在出现第二个使用方时决定。

## 四类边界归属

一期能力全部只读，不执行命令，不改变业务状态。

## 备选方案及放弃理由

- **语义服务直接读取模型源 YAML**：少一个生成步骤，但运行时会依赖代码仓，也无法锁定发布的模型版本（标准第 6.5 节）。
- **按元素类型各提供一套接口**（对象接口、规则接口……）：参考材料第四节已指出应围绕使用任务设计少量稳定入口；按类型拆分会让 Harness 自己拼装闭包，等于各自组装上下文。
- **第一版就做 MCP 服务**：目前只有一个使用方，进程内调用最简单；契约固定后再包成 MCP，成本很低。

## 后果与风险

- 知识包包含来源文档快照。来源文档有客户资料时不能直接打包；当前来源文档不含真实客户资料，以后加入时需先确定脱敏或排除规则。
- `evaluate_rule` 复用现有校验器的三值判定逻辑，判定结果与模型测试一致；Harness 需要把用户描述正确转成事实，转错会得出错误判定。评测集中的规则类题目用于发现这类错误。
- `get_state_actions` 依赖命令的前置状态定义，模型状态改动会直接影响回答，这正是“模型变了，回答跟着变”的预期。
