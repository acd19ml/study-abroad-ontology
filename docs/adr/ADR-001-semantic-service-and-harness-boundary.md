# ADR-001：业务语义服务与 Agent 运行框架的边界

- 状态：提议
- 日期：2026-11-02
- 相关模型元素：`ctx.ps.preparation` 全部元素；模型源 `model/`，元模型 `model/meta/model.schema.json`
- 参考：用户提供的《业务语义平台与 Agent Harness 的边界设计》《语义平台应该向 Agent Harness 提供哪些消费能力》（2026-11-02，原为 ERP 场景）；实践标准第 3 章、第 6.2–6.6 节。

## 背景

用户的目标是：建好业务世界模型后能准确搭建系统，并把业务架构、应用架构、信息架构串起来；之后把 Agent 作为 AI 客服，用来代查、代操作、问规则、问操作。Agent 不接入代码仓，只通过业务模型知识在限定范围内推理、回答和操作。

第一版是只读的网页问答 AI（[范围草案](../proposals/model-qa-agent-v0.1.md)）。在动手前需要定下：哪些能力属于“业务语义”这一侧，哪些属于让 Agent 跑起来的运行框架（下称 Harness），以免两边重复建设，或者把业务规则写进提示词。

## 决策

### 1. 两侧职责

**业务语义服务**负责定义、治理并提供业务的标准语义、规则、命令契约和执行约束，以统一接口对外提供可发现、可解释、可判定，以及将来可执行的业务能力。它由模型源生成，不是第二个修改入口。

**Harness** 负责理解用户目标、管理对话与上下文、安排调用顺序、调度语义服务、处理失败重试，并向用户呈现结果。

涉及业务正确性与业务安全的判断，必须由语义服务或可信执行服务完成，不能只靠模型推理或提示词约束（标准原则“契约优于上下文”）。

一句话原则：**Harness 可以决定下一步调用哪个能力，但不能自行发明在什么业务条件下该怎么做。**

### 2. 本项目中两侧各是什么

| 侧 | 本项目中的组成 | 来源 |
|---|---|---|
| 业务语义服务 | 模型源；由生成器产出的“模型知识包”；在知识包上提供查询与判定的语义服务；将来的控制层与受控执行服务 | 由模型生成，见 [ADR-002](ADR-002-semantic-service-contract.md) |
| Harness | 网页问答 AI 的运行程序：调用大模型、工具循环、对话状态、流式输出、运行记录 | 采用现成框架，不自建，见 [ADR-003](ADR-003-model-qa-web-v1.md) |

### 3. 参考材料的分层与本项目元模型的对应

参考材料按 S2A 三层（L1 业务语义、L2 场景与解析映射、L3 工具）划分。本项目不引入 S2A 的 21 类对象，继续使用实践标准第 5 章的元模型，对应关系如下：

| 参考材料的层 | 本项目元模型中的元素 | 说明 |
|---|---|---|
| L1 业务架构语义 | 上下文、业务对象及属性、关系、状态、术语（`CONTEXT.md`） | 已具备 |
| L2 场景、规则与方案 | 场景画布（场景）、规则、人工决策点、策略、命令的前置状态与状态转换 | 参考材料中的“业务方案 / 合法路径”，在本模型中由状态转换、命令前置状态和规则共同表达，不另设“方案”元素 |
| L3 工具 | 命令（一个命令对应一个工具）、事件、扩展点；实现映射（阶段 4） | 工具定义由命令生成（标准第 6.2 节） |
| 跨层映射 | 稳定 ID 与 `refs`；实现映射 | 三种架构依靠同一套 ID 串起来 |

这样，参考材料所说的业务架构、应用架构、信息架构在本项目中的落点是：业务架构为价值层与业务层；信息架构为对象、属性、关系，再经实现映射落到数据表；应用架构为四类边界、语义服务、控制层与扩展点（本组决策记录）。

### 4. 明确不做的设计

参考材料第六节的禁止项全部采纳：

- 不把全部模型元素一次放进提示词，按问题逐级取用。
- 业务规则不只写在 Agent 的系统提示词里。规则判定由语义服务按模型执行，系统提示词只写回答格式与行为约束。
- Harness 不自行推测对象间的业务关系，只使用模型声明的关系。
- 不向 Agent 暴露通用查询或通用写入能力（标准第 6.2 节），将来的查询与写入都经受控服务。
- 业务语义的最终版本只在模型源维护，Harness 不维护自己的版本。

## 四类边界归属

本记录不涉及具体命令，命令的边界划分见 [ADR-004](ADR-004-ps-command-boundaries.md)。

## 备选方案及放弃理由

- **把整个模型导出成一段长提示词给大模型**：实现最简单，但规则无法强制执行，模型版本难以追溯，上下文中的无关内容会干扰判断。属于标准第 11 章的反模式“规则只在提示词里”“各自组装上下文”。
- **自建 Agent 运行框架**：对话、工具循环、流式输出、重试都是通用能力，自建成本高且不增加业务价值。参考材料第二节 B 类能力应交给 Harness。
- **采用 S2A 的 21 类对象作为元模型**：会与实践标准的元模型并存两套语法；本项目目前一个场景，现有元模型已足够表达。需要“方案”等新元素时，按元模型扩展单独评审。

## 后果与风险

- 语义服务成为 AI 客服的唯一业务知识来源，模型的缺口会直接表现为答不上来。这是预期结果：缺口经评测发现，再回到模型修订。
- 第一版只读，“受限”主要靠语义服务只提供只读能力，加上回答约束。代操作上线前，必须具备控制层与执行前检查（标准第 6.3、6.6 节），不能以第一版的提示词约束代替。
- 参考材料中的“场景识别”在本项目只有一个场景，暂不建设；扩展到第二个场景时再评估。
